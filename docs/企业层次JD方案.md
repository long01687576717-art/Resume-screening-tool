# 企业层次 JD 知识库方案

**目标**：同一个岗位类别，头部平台 / 知名平台 / 一般平台分别要求什么（暂不分行业）。两个用途：
① HR 拿自己的 JD 和更高层次公司的同岗位要求对比；② 没有 JD 时，HR 选"岗位 + 企业层次"，直接用画像当要求模板。

**为什么要新来源**：现有 1596 份 24365 JD 中一般平台 78%、知名平台 18%、头部平台只有 2%（每个岗位 0～2 份）。
大公司的校招职位发在自己的官网或招聘系统（ATS）上。

企业层次沿用知识库：`KnowledgeBase().match_company(公司名).tier`（头部平台 / 知名平台 / 一般平台 / 机关 / 事业单位）。

"没有 robots.txt"指请求 /robots.txt 返回 404 或网站首页（单页应用的兜底页），按惯例视为不限制。

## 二、高质量 JD 的定义（`matching/jd_quality.py`）

原则：一份 JD 只有能当作"这一层次的公司对这个岗位的真实要求"的样本时才算数。不打总分，**4 道门槛全部通过**才进入统计，另记 2 个标记。
阈值都是文件开头的常量。

| 门槛 | 规则（实现） |
|---|---|
| 1 完整 | 岗位职责和任职要求都有；各自拆成条目后 ≥3 条，或 ≥80 字（`MIN_ITEMS`、`MIN_CHARS`）。小标题行（"★工作内容："）不算条目 |
| 2 具体要求 | 任职要求里 ≥3 项能在简历上核对的具体要求（`MIN_CONCRETE`）。**AI 提取之前的近似**：能力词典关键词（长词优先、不重复计数，排除通用办公和"协同组织"这类软素质领域）+ 证书 / 资格 / 语言等级正则 + 英文工具名（排除 Office、Word、PPT 等） |
| 3 职责具体 | 具体职责占比超过一半（`DUTY_SPECIFIC_SHARE`）。空泛职责：写了"领导交办 / 其他工作 / 服从安排"；或去掉编号后不到 12 个汉字且没有词典词；或两字词里泛词（在 ≥20% 的 JD 里出现，与 `matching/jd.py` 的 `VAGUE_SHARE` 相同）过半 |
| 4 真实单一 | 职位名称不是多个岗位（与 crawl_jd.py 的 `MULTI_ROLE` 相同）；正文没有"岗位一 / 岗位二"或两段"岗位职责"；内容相同的只留第一份（职责 + 要求的 md5，与 crawl_jd.py 相同）；公司能定到头部 / 知名 / 一般平台（机关、事业单位不算） |

| 标记（只记录） | 规则 |
|---|---|
| 5 分清必须 / 加分 | 任职要求里有"优先 / 加分 / 更佳 / 者佳 / 为佳" |
| 6 要求与职责一致 | 任职要求涉及的能力领域，有一半以上也出现在职责里；要求里没识别出领域时记"无法判断" |

结果对象 `QualityResult`：`passed`、每道门槛的 `Gate(passed, reason, detail)`、`flags`；`explain()` 输出中文说明。
批量用 `check_batch(rows, kb)`（负责去重和定档）。

**自检**（`python -m matching.jd_quality`，4 份 `samples/jd/`）：通过 2 份。
- 数据分析工程师、采购专员：通过
- 人力资源专员：未过"完整"（职责只有 2 条、76 字）
- 数据分析专员（要求很少）：未过"完整""具体要求"（要求 2 条 50 字，具体要求 0 项）——这份本来就是"要求很少"的反例

## 三、层次画像规则（`tools/build_tier_profiles.py`）

1. 合并 24365（`data/jd_raw/ncss_jd.jsonl`）和官网 JD（`data/company_jd/company_jd.jsonl`），按内容去重；24365 的公司用 `match_company` 定层次
2. 只用通过 4 道门槛的 JD
3. 每个（岗位类别 × 企业层次）**至少 15 份**高质量 JD（`MIN_JD`）才生成画像，否则写"样本不足"和现有份数，不凑数
4. 够数的格子用 deepseek-flash 提取，**提示词沿用 `matching/jd_extract.py`，不改**；输入文字拼法与 build_job_profiles.py 相同，24365 已提取过的直接用缓存；统计复用 `build_job_profiles.aggregate`（核心 ≥50%、常见 ≥20%）
5. 画像额外记录公司数和最大一家公司的占比（`top_company_share`），头部平台公司少，一家占比过高时要谨慎看
6. 输出 `knowledge/job_profiles_tiers.json`（只有统计比例和技能名，不含 JD 原文）

## 四、本地运行步骤

```
# 1. 爬官网校招 JD（有缓存，可断点续爬；每秒最多 3 次请求；约 2 分钟）
python tools/crawl_company_jd.py
python tools/crawl_company_jd.py --only 腾讯,百度        # 只爬几家

# 2. 不调用 AI，先看质量门槛通过率和每格份数
python tools/build_tier_profiles.py --dry-run

# 3. 提取并生成画像（需要 DeepSeek Key，默认 deepseek-flash；24365 部分走缓存）
python tools/build_tier_profiles.py

# 自检质量门槛
python -m matching.jd_quality
```

爬到的 JD、缓存、`quality.jsonl` 都在 `data/`（已在 .gitignore），不上传。

## 五、试爬结果（2026-09-30）

7 家公司官网共 858 个校招职位，归类、去重、每类每家最多 5 份后保留 334 份（头部 258、知名 76）。
与 24365 的 1596 份合并后跑 `--dry-run`：

| 来源 | 份数 | 通过门槛 |
|---|---|---|
| 24365 | 1596 | 355（22%） |
| 腾讯 / 百度 / 美团 / 京东 / 网易 | 62 / 44 / 65 / 61 / 26 | 42 / 36 / 55 / 52 / 22（68%～85%） |
| 三一集团 / 360 | 55 / 21 | 34 / 19（62% / 90%） |

24365 通过率低，主要是 897 份 JD 没拆出"任职要求"（原文没有小标题时 crawl_jd.py 全部算职责），门槛 1、2 都会不过。

高质量 JD 份数（★ = 够 15 份，可出画像）：

| 岗位类别 | 头部平台 | 知名平台 | 一般平台 |
|---|---|---|---|
| 后端开发 | ★24 | 9 | ★20 |
| 算法工程师 | ★25 | 9 | ★15 |
| 数据分析 | ★16 | 10 | ★18 |
| 用户与内容运营 | ★20 | 7 | 11 |
| 产品经理 | ★18 | 5 | 9 |
| 前端开发 | 5 | 4 | ★34 |
| UI与视觉设计 | 11 | 0 | ★27 |
| GIS与测绘 | 0 | 8 | ★18 |
| 其余 20 个类别 | 0～13 | 0～10 | 0～14 |

结论：头部平台目前只有互联网岗位够数；**知名平台没有一个格子够数**，一般平台只有 6 格够数。

## 六、风险和局限

- **头部 = 互联网**：已接入的头部公司全是互联网公司，财务、审计、咨询、金融等职能岗的头部样本几乎没有（四大、咨询、券商未调查）。画像会带明显的行业色彩。
- **门槛 2、3 是词典近似**：词典缺材料、机械、法律细分等领域词，这些岗位的具体要求会被低估（例：某材料工程师要求写了"失效分析、材料选型"，只识别出 1 项）。有了 AI 提取结果后，可改用提取出的技能 + 业务能力项数判断。
- **官网职位按名称归类**：`job_categories.json` 的 title 规则原本配合关键词搜索使用，官网是全部职位直接归类，所以比较前去掉"工程师"，并对土木建筑、金融投资改用窄规则；"测试开发""全栈"之类名称仍可能归错。
- **每家每类最多 5 份**（24365 用 3 份）：头部公司只有 5 家，上限 3 时每格最多 15 份，刚好卡在门槛上。
- **接口会变**：官网改版、开始要求签名或返回 403 时，爬虫会停下这个来源并提示，不绕过；网易等的项目号每年变，已改成从导航接口自动读取。
- 官网 JD 更新快，同一次爬取只代表当季校招。
